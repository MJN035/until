# 유형별 경계선·알고리즘 설계 (기획)

> ⚠ **표본: minjun 코퍼스 148건, 전기공학 전공 편향 있음 — 일반화 금지.**
> ⚠ **기획 문서다 — 구현 아님.** 유형 정의·빈도·예시는 `assignment_taxonomy.md`(T0~T8) 참조.
> 검증 메모(g절)는 mock 백엔드 실행 결과라 **경계선 위치·결정 지점 생성 로직만** 검증한
> 것이고 본문 품질은 검증 대상이 아니다(mock 초안은 고정 템플릿).

## 0. 읽는 법

- 파이프라인: `Capture(파싱, 토큰 0) → Understanding(spec 추출·유형 분류) →
  Context(수업자료·내 파일·말투·지난 제출물) → Execution(경계선 초안) → Boundary(검증)`.
- 경계선 4분류(`boundary/rationale.py`): 가치판단·관점/논지 · 진로·경험 · 취향·스타일 ·
  범위·선택. "submission에서 나만 쓸 수 있었던 대목"이 경계선 후보라는 원칙으로,
  각 유형의 spec ↔ 실제 submission을 나란히 놓고 선을 그었다.
- LLM 호출 규모는 현 파이프라인 기준(understanding 1 + 요소분해 1 + execution 1 +
  reask ≤2)이 "표준 3~5콜"이고, 유형별로 증감을 적는다. (기여자 B 요청: 비용 감각)

## T1a. 소감문 (29건, 19%)

**a. spec ↔ submission 비교.** spec: "강의 내용을 합쳐서 공백 포함 400자 이상"(전기·정보
세미나 1, 매주 동일). 실제 제출물 16건의 구조는 놀랍도록 일정: ① 교수·연구실별 강의 사실
요약("서종모 교수님께서 연구하고 계시는 '인공망막'…") ② 개인 반응("수강해보아야겠다고
생각했다") ③ 진로·수강계획 연결("'제어공학개론'을 수강한 뒤에 다시…").

**b. 자동으로 채울 수 있는 것.** 구조(사실→반응→연결), 분량 맞춤(400자), 문체(내 지난
소감문 — series.py로 주입 가능, 구현됨), 문장 다듬기. **단, 강의 '사실'의 원료가 eTL에
없다** — 세미나 강의자료 첨부 0건(제출물에서 "발표자료 올려주시길 요청"이 나올 정도).

**c. Draft 경계선.**
- `[[DECISION: 오늘 강의에서 인상 깊었던 대목 2~3개(키워드면 충분)]]` — **경험**. 이게 이
  유형의 유일한 필수 입력이자 유일한 경계선. 실제 제출물의 ②③이 전부 여기서 파생된다.
- 진로 연결 문장("이 분야 수업을 들어보고 싶다")은 **진로** — 상투 문구로 자동 생성하면
  경계선 위반이자 거짓말. 키워드 입력에 진로 언급이 있으면 반영, 없으면 생략이 맞다.

**d. 맥락 소스.** 지난 제출물 시리즈(핵심, 구현됨) > voice > course-materials(있다면).

**e. 단계별 처리.** understanding: 분량 하한·주차·강의 주제(제목에서). execution: 키워드
입력을 받아 사실 서술을 골격으로 쓰되 **키워드가 없으면 본문을 지어내지 말고 키워드 요청
결정 1개만 낸다**(현재는 일반 상식으로 채워버릴 위험 — g절). boundary: min_decisions=1.

**f. 구현 판정.** **된다.** 신규 로직은 '키워드 선입력 → 초안' 순서 하나. 소과제라
경량 모델 1~2콜(UNTIL_MODEL_LIGHT)이 적정 — 표준 5콜은 과함.

**g. 검증 메모(Phase 3).** mock 실행(`3주차 소감문` spec): reflective로 분류되나 초안이
**에세이 골격의 결정 3개**(핵심 논지 선택/반론 톤/주장 강도)를 냈다. 소감문에 '반론 수용
톤' 결정은 **범주 착오** — 게으른 떠넘김이 아니라 골격 자체가 다른 유형 것.
→ **수정안:** `understanding/skeleton.py`에 반응형 골격(사실→반응→연결) 추가,
결정 골격을 유형별로 분리(에세이 결정 3종을 공용 기본값으로 쓰지 말 것).

## T1b. 질의 (14건, 9% — 미제출 13건: 실수요 1위)

**a. 비교.** spec: "교수님들께 질문드릴 내용 작성"(주차별 동일, 순번제). 실제 제출물:
질문 3개 — 연구분야×미래산업 전망 / 연구 중 흥미로운 적용 사례 / 창업 연계. 즉 '주제 ×
관심 프레임'의 조합이다.

**b. 자동.** 강의 주제·교수명(제목·질의순번 시트 링크에서)으로 질문 후보 5~6개 생성 —
프레임(전망/사례/진로/방법론/한계)별 1개씩. 문장은 존댓말 정형이라 완전 자동 가능.

**c. 경계선.** `[[DECISION: 후보 중 실제로 궁금한 질문 2~3개 선택(또는 수정)]]` —
**취향·범위 선택**. 질문 후보 생성은 경계선 안(자료로 가능), "내가 뭘 궁금해하는가"만 사람.
AI 제안(suggest)의 '전부 수락'과 동형 — 이미 있는 UX에 얹힌다.

**d. 소스.** 지난 질의 제출물(프레임 재사용) > 강의 주제. **e. 처리.** understanding에서
대상 교수·주제 추출 → execution이 후보 목록 생성 → boundary가 선택 결정 1개.

**f. 판정.** **된다, 가장 싸다.** 1콜(후보 생성)로 충분. 미제출 13건이 여기 몰린 걸 보면
'매주 자동 후보 + 원탭 선택'이 실사용 가치 최상위.

**g. 검증 메모.** mock: 에세이 결정 3개가 그대로 붙음(T1a와 동일 패턴). 질의에 "핵심 논지
선택"은 무의미 → 유형별 골격 필요성 재확인.

## T2. 조별 활동 기록 (11건, 7%)

**a. 비교.** spec: "첨부파일 양식 참고 / 각 조원별 내용 포함 / 사진 없을 시 출석 인정 불가 /
pdf 변환 후 업로드". 양식(hwp, 이번에 파싱됨): 날짜/조/작성자/참여자/불참자/활동내용/활동사진.

**b. 자동.** 양식 구조 재현(칸 유지 — formfill 계열), 활동 사실을 받아 '각 조원별 내용'
요건에 맞는 서술로 정리, pdf 내보내기(구현됨).

**c. 경계선.** 핵심: 이 유형의 빈칸 대부분은 판단이 아니라 **사실**(누가 왔고 뭘 했나)이다.
사실을 [[DECISION]]으로 포장하면 안 되고(결정이 아님), AI가 채우면 날조다. →
`[[DECISION: 이번 활동 사실 — 날짜·참여자·한 일(한 줄씩)]]` 형태의 **사실 입력 게이트**
1개로 묶는 게 맞다. 활동사진은 Until 범위 밖(명시 안내).

**d. 소스.** 양식 첨부(hwp) + 지난 회차 제출물(서술 밀도 참고). **e. 처리.** capture가
양식 파싱 → execution이 사실 입력을 칸별 서술로 → 제출용 pdf.

**f. 판정.** **절반 된다.** 사실 입력 UX(칸별 입력)가 관건 — 텍스트 1칸 입력으론 어색.
조별 공동 산출물이라 문체 학습에서 제외(구현됨)는 유지. 1~2콜.

**g. 검증 메모.** mock: hwp 양식이 첨부로 파싱돼 들어갔지만 초안은 에세이 논지 결정을 냄.
양식 감지(formfill) → '칸 채움 모드'로 전환되는 분기가 이 유형에선 필수라는 게 확인.
→ **수정안:** 양식 첨부 + 짧은 spec이면 form-first 골격을 기본값으로.

## T3. 실험·실습 레포트 (9건, 6%)

**a. 비교.** spec이 제목뿐("실습2 레포트", 본문 30자, 첨부 0). 실제 제출물: 결과 스크린샷
·사진 중심 docx(20MB 초과 6건). 명세(실습지)와 데이터(실측)가 모두 eTL 밖.

**b. 자동.** 이론 배경·목적·방법 서술 골격, 고찰 프레임("오차 원인 후보 → 판단은 사람").
**c. 경계선.** 결과 해석·오차 원인 판정(**판단**), 실측 데이터·스크린샷(**사실**, AI 불가).
**d. 소스.** my-files(실습지 pdf를 학생이 직접 첨부 — 웹 '내 자료' 업로드, 구현됨) 없으면
원료 부족. **e. 처리.** 자료 없으면 readiness가 '자료 없음' 경고(구현됨)를 내고 초안은
프레임까지만.

**f. 판정.** **골격만 된다.** 자동 수집이 불가능한 유형의 대표 — '내 자료 업로드' 유도가
제품 답. 표준 3~5콜.

**g. 검증 메모.** mock: report로 분류(이번 분류기 보강 반영), 결정 2개(오차 원인 방향 /
개선 방향)는 **적절한 경계선** — 이 유형의 골격은 현행 유지. 다만 원료(실습지) 없이 돌리면
일반론 초안이 되는 건 여전 — 자료 요청을 결정보다 앞세우는 UX 필요.

## T4. 문제풀이 숙제 (6건, 4%) — ⚠ 윤리 게이트 필요

**a. 비교.** spec: 문제지 pdf + 배점 + **"종이에 작성한 답안의 스캔이나 사진, 또는 손글씨를
그대로 남긴(폰트 변환하시면 안됩니다)"**(물리학 1 숙제 1~4 공통). 대필 산출물 제출을
규정으로 차단한 유형.

**b~c. 자동/경계선.** 기술적으로는 풀이 생성이 가능(FACTUAL, 결정 0~1). 그러나 이건
경계선(사람 판단) 문제가 아니라 **규정 준수** 문제 — "손글씨 그대로" 신호가 있으면 최종
답안 생성 자체가 부적절. Draft 경계선 철학의 자연 확장: *사람의 고유 판단*뿐 아니라
*사람이 해야 한다고 규정된 것*도 넘지 않는다.

**d~e. 처리 제안.** understanding에서 대필 금지 신호(손글씨/스캔/자필/본인이 직접) 감지 →
**학습 보조 모드로 강등**: 개념 정리·유사 예제 1개 풀이 시연·검산 체크리스트만 산출,
최종 답안은 내지 않음. UI에 이유 명시("이 과제는 자필 제출이 규정이에요").

**f. 판정.** 신호 감지는 결정적(정규식)으로 싸게 된다. 학습 보조 모드는 신규 산출물 형태
(중간 난이도). **이 게이트는 제품 신뢰의 문제라 우선순위 높음.**

**g. 검증 메모.** mock(숙제1, 문제지 pdf 첨부): problemset 분류·결정 1개("명시되지 않은
초기 조건")로 정형 처리 자체는 맞으나, **손글씨 요구를 아무도 감지하지 않았다**. 현재
파이프라인은 이 숙제의 완성 답안을 그대로 써준다 — 유일하게 '잘 작동해서 문제'인 케이스.

## T5. 코드·구현 (6건, 4%)

**a. 비교.** spec: "각 문제의 출력 사항을 반드시 지켜"(컴퓨터의 개념 및 실습) — 채점
자동화 전제. 제출물: zip·ino.
**b~c.** 스펙 준수 골격·구현·주석까지 자동(FACTUAL, min_decisions=0 구현됨). 경계선은
설계 선택지가 갈릴 때만(자료구조 선택 등 **범위·선택**).
**d~e.** 첨부 zip 안의 스켈레톤 코드가 명세 — **zip 파싱이 현재 미지원**(경고 처리)이라
Capture 갭. 산출도 '코드 파일'이 아닌 텍스트라 제출까지 수작업.
**f. 판정.** 초안(코드 텍스트)까지는 된다. zip 내 텍스트 파일 선별 파싱은 저비용 확장
후보. 표준 3~5콜.
**g. 검증 메모.** mock: 정형 분류·결정 1개 — 방향 맞음. canned 결정 문구("이상적 소자
가정")가 코드 과제엔 안 맞는 건 mock 한계로 기록만.

## T6. 데이터 분석 노트북 채움 (6건, 4%)

**a. 비교.** spec: "아래의 파일을 다운로드하여 수정 후 html 파일로 제출"(통계학실험,
Rmd 첨부. `중간고사`·`기말고사`도 실체는 동일한 Rmd 실기).
**b~c.** Rmd는 텍스트 — 문제 청크/빈 청크 구조 파싱 가능. 코드 골격+해석 서술 자동,
해석의 결론("유의하다고 볼 것인가")은 **판단** 경계선. R 실행·html 렌더는 사람.
**d~e.** intro 첨부(Rmd)가 명세의 전부라 자동 수집과 궁합이 좋다. `.rmd`가 텍스트 폴백
으로 이미 읽힘(확장자 미등록이라 plain text 취급 — 코드 청크 인식은 없음).
**f. 판정.** **된다.** Rmd 청크 인식(결정적 파서)만 추가하면 품질이 크게 오름. 3~5콜.
**g. 검증 메모.** mock: 정형으로 흘러 결정 1개. Rmd 원문이 통짜 텍스트로 들어가 문제
단위 구조가 사라짐 — 청크 인식이 있어야 항목별(문제별) 초안이 가능하다는 확인.

## T7. 에세이·글쓰기 (11건, 7%) — 현 파이프라인의 코어

**a. 비교.** 사례 탐색형(현대경제 `과제1`): "사례 찾기 → 주장·근거 정리 → 수업 원리와 왜
배치되는지" — 실제로는 ①사례(외부 사실) ②원리 연결(자료로 가능) ③평가(판단)의 3층.
과정 분해형(대학 글쓰기): `주제_주제문_개요` → `서론 작성` → `서론 수정` 제출물을 보면
회차마다 **직전 회차 산출물이 입력**이고, `서론 수정`은 조원 피드백 반영까지 요구.

**b~c.** 현 경계선 설계(관점·논지/톤/마무리)가 실제와 부합 — `서론 수정` 제출물의 "인간의
삶에서 가장 중요한 것은 무엇일까"(첫 문장 후킹 선택)나 주제 선택("건강한 취침자세")이
전형적 **관점/취향** 결정. 사례 탐색형의 '사례'는 **자료에 없는 외부 사실** —
`[[DECISION: 분석할 사례]]`로 남기는 게 맞고, 원리 연결·구조는 자동.
**d~e.** 과정 분해형엔 시리즈 맥락(구현됨)에 더해 '내 직전 단계 산출물'을 1순위 소스로.
**f. 판정.** **이미 된다**(P5 라이브 검증 과제가 이 유형). 표준 3~7콜.
**g. 검증 메모.** mock(`정의·비교를 이용한 글쓰기`): essay 분류, 분량(2,500~3,000자) 감지,
결정 3종 — **잘 그어진 경계선의 기준 사례**. 유일한 보완: '조원 피드백 반영' 같은 회차 간
입력을 결정으로 명시화하는 것.

## T8. 발표·스피치 (11건, 7%)

**a. 비교.** `피피티 제출`(spec은 마감 안내뿐), CE2 `... Speech Outline`(영어, docx 양식
첨부), `Demonstration Video Speech`(유튜브 업로드 절차 안내가 spec의 대부분).
**b~c.** 개요·스크립트·슬라이드별 불릿 자동(영어 포함). 주제·스토리 선택은 **관점**,
발표 스타일은 **취향** 경계선. 영상 촬영은 범위 밖. 단, 글쓰기 결과물을 발표로
변환하는 과제는 선행 제출물의 확정 주제를 유지하고 발표 범위·시간만 질문한다.
**d~e.** 발표는 본체(글·주제)가 다른 과제의 파생물인 경우가 많아(글쓰기 피피티 = 기말
과제 발표) — 같은 과목 내 원본 과제 산출물이 1순위 소스.
**f. 판정.** 개요·스크립트와 16:9 pptx 생성까지 **된다**. 디자인 조건이 없으면
내용량에 맞춰 자동 결정하고, 미해소 결정은 슬라이드에서 명시한다. 3~5콜.
**g. 검증 메모.** `test_presentation_conversion`: 선행 단계 순서, 조별·미래 정보 제외,
남은 질문 축소, OOXML 패키지/XML/텍스트 왕복과 웹 다운로드 배선을 오프라인 검증.

## 9. 유형 공통 관찰 (Phase 3 종합)

### 구현 메모 — 분산 명세 수집(세 번째 과목별 알고리즘)

실사용 확인상 문제·코딩 과제의 명세는 제출함에 붙지 않을 수 있다. 물리 과제는
주차 강의자료 PDF 중간/마지막에 문제가 있고, 코딩 요구사항은 별도 토론/코딩
게시판에 올라온다. 따라서 `distributed_spec.py`가 제출함 제목의 과제 번호·주차를
키로 과목 파일·모듈·게시글을 모으고, PDF 전체에서 명세 표식 주변을 발췌한다.
명세가 연결되면 generic `과제 N`의 essay 오분류를 problemset/code로 교정한다.
번호 경계(`3` ≠ `13`)와 다른 회차 혼입 금지를 결정적으로 강제한다.

1. **경계선 오류의 주 패턴은 '떠넘김'이 아니라 '골격 착오'** — 반응형(T1a/T1b/T2)이
   에세이 결정 3종을 받는다. 결정의 '개수'는 가드가 지키지만 '종류'는 아무도 안 지킨다.
   → 유형별 결정 골격(무엇이 결정이어야 하는가)을 skeleton에 명시하는 게 최우선 수정안.
2. **원료 없는 유형이 초안을 지어낼 위험**(T1a 키워드 없음, T3 실습지 없음) — "자료가
   없으면 본문 대신 자료 요청 결정을 내라"는 규칙이 필요(경계선의 소극적 형태).
3. **윤리 게이트 부재**(T4) — '대필 금지 신호' 감지는 Draft 경계선 철학의 규정 버전.
4. **잘 되는 것 확인:** 유형 라우팅(T3→report, T4/T6→정형), 분량 감지(T7), 에세이 경계선
   (T7), hwp 양식 파싱(T2), 자리표시 제외(T0).
