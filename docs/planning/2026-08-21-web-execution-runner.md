# 웹에서도 코드를 실행한다 — Until Runner (별도 서비스)

작성 2026-08-21 · 사용자 지시: "로컬 런타임에서 할 수 있는 걸 웹에서도 할 수 있게.
별도의 서버를 하나 만들어도 괜찮아"

## 왜 별도 서비스인가

로컬 런타임의 검증기 중 **모델이 필요 없는 것은 이미 웹으로 옮겼다**(커밋 `6c8b333`).
남은 것은 **코드 실행** 하나다. 그런데 실행은 성격이 완전히 다르다:

- 돌리는 코드는 **신뢰할 수 없다**. LLM이 쓴 코드 + 학생 과제의 테스트다.
- 웹 프로세스 안에서 돌리면 세션·eTL 토큰·결제 원장이 같은 주소공간에 있다.
- 실행 서비스는 **채굴·스팸의 표적**이다. 인증·할당량·상한이 없으면 안 된다.

그래서 웹 앱은 **코드를 절대 실행하지 않는다.** HTTP로 러너에게 맡기고 결과만 받는다.

## 절대 규칙

1. **격리를 증명하지 못하면 실행하지 않는다.** 러너는 기동 시 자기 격리를
   `runtime.sandbox_check`로 **스스로 시험**하고, 통과 못 하면 실행 요청을 전부 거절한다
   (`503`). 로컬 런타임의 fail-closed와 같은 기준 — 코드로 확인 못 한 격리는 없는 것이다.
2. **명령은 요청자가 정하지 않는다.** 러너가 아는 명령(`KERNEL_ALLOWED_COMMANDS`)만,
   서버가 조립한 단계만 실행한다. 요청 본문에 argv를 실어 보내는 API를 만들지 않는다 —
   그건 원격 셸이다.
3. **네트워크 없음 · 시간 상한 · 크기 상한 · 출력 상한.** 전부 코드로 강제한다.
4. **인증**: 공유 비밀 HMAC. 서명 없는 요청은 본문을 읽지도 않는다.
5. **웹은 실패해도 그냥 진행한다.** 러너가 없거나 죽어도 초안·제출은 지금과 똑같이
   동작하고, 점검 항목 하나가 '실행 못 함'으로 뜰 뿐이다.
6. **기본은 꺼짐.** `UNTIL_RUNNER_URL`이 없으면 코드 경로가 지금과 완전히 동일하다.

## 구조

```text
브라우저 → until-app (웹)            → until-runner (별도 서비스)
                │ 코드·테스트 파일         │ 격리 자체검증 통과해야 기동
                │ HMAC 서명 요청           │ 컨테이너/샌드박스 안에서 실행
                └← RunResult ─────────────┘ 네트워크 0 · 타임아웃 · 출력 상한
```

재사용(새로 만들지 않는다):
- `runtime.models.RunStep` / `RunResult` — 로컬과 **같은 계약**
- `runtime.security.validate_step` / `KERNEL_ALLOWED_COMMANDS` — 같은 천장
- `runtime.sandbox_check` — 러너의 자기 격리 시험
- `runtime.boundary.SubprocessBoundary` — 실제 프로세스 실행

## 단계

### [x] R1 — 프로토콜 (`until/runner/protocol.py`)
요청/응답 스키마, HMAC 서명·검증, 크기 상한. 순수 함수·테스트 가능.

### [x] R2 — 러너 서비스 (`until/runner/service.py`)
`POST /run` + `GET /healthz`. 기동 시 격리 자체검증. 임시 작업공간에 파일을 풀고
서버가 조립한 단계를 실행 후 정리.

### [x] R3 — 웹 클라이언트 (`until/runner/client.py`)
서명해서 호출, 타임아웃, 실패는 비치명. 웹은 이것만 안다.

### [x] R4 — 웹 연결
코드 계열 과제에서 초안의 파이썬 블록 + 과제가 준 테스트 첨부로 작업공간을 만들어
러너에 보내고, 결과를 제출 점검 항목으로 보여준다. **UI 변경 없음**(점검 목록에 한 줄).

### [x] R5 — 배포
`deploy/Dockerfile.runner` + `render.yaml`에 서비스 추가(기본 비활성). 문서.

### [x] R6 — 검증
오프라인 테스트 + **실제 Docker로** 격리·타임아웃·네트워크 차단 실측.

## 실측 결과 (2026-08-21, 내부망 컨테이너)

| 시나리오 | 결과 |
|---|---|
| 맞는 풀이 | `succeeded` → 점검에 "테스트를 통과했습니다" |
| 틀린 풀이 | `failed` → "FAILED (failures=1)" |
| 문법 오류 | `failed` → SyntaxError |
| **코드가 네트워크 시도** | 연결 실패 — 막힘 |
| **무한 루프** | 5초에 `timeout` |
| **서명 없는 요청** | `400` 거절 |
| 격리 안 된 컨테이너 | 기동은 되나 `/run` 전부 `503` |
| 러너 미설정 | 웹이 완전히 조용함(`run_check=None`) |

## 만들면서 잡은 것

- **`sandbox_check`의 '밖'은 격리 방식마다 다르다.** 로컬 래퍼는 작업공간의 부모가
  밖이지만, 컨테이너에서 부모는 대개 tmpfs라 써져도 무해하다. 기본값을 그대로 쓰면
  멀쩡한 컨테이너 격리를 불합격시킨다 → `escape_targets`를 부르는 쪽이 정하게 했다.
- **네트워크 대조군도 마찬가지.** 로컬 래퍼는 '밖에서는 나가지는가'를 비교해야 하지만,
  러너는 자기 자신이 샌드박스라 밖이 없어서 대조군이 늘 같은 결과를 낸다 →
  `network_control=False`. 안 고쳤으면 제대로 격리한 컨테이너가 영영 `unknown`이었다.
- `until/runtime/__init__.py`가 형제 모듈을 임포트해서 Dockerfile에서 파일을 골라
  담으면 깨진다 → `until/runtime/` 통째로 복사(전부 표준 라이브러리라 무해).

## 남겨 둘 것

Render 같은 일반 PaaS 컨테이너는 **네트워크 송신을 막기 어렵다.** 그런 곳에 러너를
올리면 자기검증이 network를 통과 못 해 기동은 되지만 실행은 거절한다 — 그게 맞는
동작이다. 실제로 켜려면 네트워크를 막을 수 있는 곳(자체 VM·gVisor·네트워크 정책이
있는 클러스터)에 올려야 한다. 이 제약을 문서에 분명히 적을 것.
