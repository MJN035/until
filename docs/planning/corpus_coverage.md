# 109개 과제 전수 처리경로 감사

## 완료 기준

사용자가 확인한 eTL 제출 대상 109개 각각이 다음 중 하나를 가져야 한다.

1. 전용 처리 알고리즘과 먼저 확보할 근거
2. 실제 경험·팀 합의·실측처럼 Until이 만들 수 없는 정보에 대한 구체 질문
3. 제출물이 없는 성적부 항목이라는 명시적 제외 판정

단순 `기타` 분류는 커버로 세지 않는다. 원문 코퍼스는 개인정보 때문에
`_until_work/`에만 두고 저장소에는 집계와 결정적 감사기만 남긴다.

## 네 번째 이후 구현

- **4 — R Markdown 노트북:** YAML, 문제 순서, R 청크 옵션, 코드/해설 슬롯을 보존한다.
  데이터가 없으면 수치와 그래프 결과를 만들지 않고 실행 후 채울 결정으로 남긴다.
- **5 — ZIP 코드 프로젝트:** 압축을 풀거나 코드를 실행하지 않고 PDF/README/소스/테스트의
  파일 경계를 읽는다. 경로 탈출, 과대 항목, 과다 파일, 총 텍스트 크기를 제한한다.
- **6 — 팀 프로젝트:** 팀 합의본, 공유 파일, 본인 담당 범위, 평가 기준을 먼저 모은다.
  다른 팀원의 판단이나 미완성 담당분을 임의로 대신 작성하지 않는다.
- **전수 라우터:** 기존 질의·발표변환·분산명세 알고리즘과 반복 소감, 활동 양식,
  실험 보고서, 단계형 글쓰기, 코드 과제를 하나의 결정적 처리경로로 연결한다.

## 2026-08-04 실제 파이프라인 검증

라우팅만으로 완료 처리하지 않도록 `run_corpus_validation.py`를 별도로 만들었다. 과제마다
과제 페이지와 교수 첨부를 실제로 읽고 다음을 모두 검사한다.

- Capture 파싱 및 HTML·대체문자 오염
- legacy와 unit 두 파이프라인 실행
- BoundaryGuard 통과, 초안·유형·처리경로 존재와 두 경로의 라우팅 일치
- readiness의 양식·분량·자료·경계선·가짜 인용 경고 0

- 원장에는 제목·원문·학번 대신 과목ID+과제ID SHA-256 지문 12자리만 기록

최종 실행 결과:

- 원시 행 148개 검증
- 실제 제출 대상 처리경로 105개: legacy 105/105, unit 105/105 통과
- 성적·출석 자리표시 43개: 명시적 제외

  0이며, 미답 DECISION의 본인 경험·관점 몫 때문에 생기는 분량 경고와 과거 마감 경고만
  정상적인 사용자 입력 대기 상태로 기록한다.
- 정답셋 제출 파일이 있는 과제는 Rmd→HTML, ZIP→ZIP, 발표→PPTX/문서 등 형식 대조 통과

동일 입력을 두 번 실행한 비식별 원장 SHA-256도 일치해 결과 결정성을 확인했다.

## 2026-08-04 eTL 컨텍스트 비교군 배선

기존 Canvas 읽기 수집기를 코퍼스 러너에 연결했다. 과목당 한 번 조회한 파일·모듈·
공지 목록은 `_course_context/<course_id>/course_context.json`에, 과제 키워드로 추린
자료·공지는 `<과제>/etl_context/context.md`에 저장한다. manifest는 context 경로와
자료·공지·전체 source 수를 기록한다. 공지 작성자는 역할 라벨만 저장하고, Canvas
공지 전용 endpoint만 사용해 다른 학생의 Q&A·답글 본문은 저장하지 않는다. 공지 본문
자체에 들어간 실명은 아직 자동 비식별화하지 않는 명시적 잔여 위험이다.

`examples/corpus_mode_fixture` 1건을 mock으로 각각 실행한 결과 세 원장의 SHA-256이
서로 달랐다. 즉 `full = spec+직접첨부+eTL 번들`, `no_etl_context = spec+직접첨부`,
`bare = spec` 입력 차이가 실제 산출물 차이로 이어진다. live backend는 실행 전 최소
호출·토큰 추정과 확인 게이트를 거치고 실제 사용량을 원장에 기록한다.

- `full`: `99FC3B50531CA6D243E15A998996A23CBC08F538FB16726BD30CEB0B3770021A`
- `no_etl_context`: `F78A663C37D576361F359E1C87517462A2648766B10F8C322A5D84CE52F68A1A`
- `bare`: `E8BDF2039BB638219D1B29B3860F370ACA0F9431989E1EDC84E4A4B1C88F79A9`

같은 날 Canvas 읽기 API로 개인 코퍼스를 다시 수집했다. 21개 과목의 148개 과제 모두에
과제별 번들을 만들었고(일치 자료가 없는 경우도 명시적 빈 번들), 합계 863 sources =
자료 504 + 공지 359였다. 저장된 공지 작성자 역할 값은 허용 열거형 밖 0건이다.
mock 비교 결과는 다음과 같다.

- `full`: 통과 103, 제외 43, 실패 2 — `64694432AF53C96D3E575B09D2B0821811BD31081195CDC7A00177D07940FA37`
- `no_etl_context`: 통과 105, 제외 43, 실패 0 — `02EC27A193F61E71B5335AB6F754A003199EEF4F40A126F670102877CD55D7D4`
- `bare`: 통과 105, 제외 43, 실패 0 — `F0D7E44815D73A4396B9090F9A5D089DD395D531F7039F3BA866E7C5858ED2BC`

세 SHA-256은 모두 다르다. `full`의 2건은 컨텍스트가 추가된 unit mock 초안에서 결정
마커를 제외한 본문이 BoundaryValidator의 200자 하한에 못 미친 실제 실패(166자,
191자)다. `bare` 최초 실행의 ZIP 3건 실패는 입력에서 첨부를 제외하고도 검증 기대
경로에는 첨부명을 쓰던 오판이었으며, 기대 경로도 실제 bare 입력만 보도록 수정한 뒤
105/105로 통과했다. `run_corpus_coverage.py --minimum 109`는 다시 148/148을 보고했다.
