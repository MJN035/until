# P5 — 시간 축 방향: "몰아서 우선" (결정, 2026-08-05)

> P5 = "학생이 과제를 언제 처리하는가"에 Until이 베팅하는 사용 모델.
> 그때그때(분산·체크포인트 구동) vs 몰아서(마감 구동) 중 **몰아서 우선**으로 확정.
> 관련: `docs/superpowers/specs/2026-07-24-checkpoint-plan-design.md`(3단계가 이 결론
> 대기였음), `docs/TELEMETRY_SCHEMA.md` §2.7("P5 시간" 측정 필드).

## 결정

**마감 구동 원샷 완결에 최적화한다.** 인박스에서 급한 과제를 골라(⚡ 자동 선택 포함)
한 세션 안에 초안→결정→완성본→제출 점검까지 끝내는 흐름이 Until의 1차 사용 모델이다.

## 근거

- 학생 현실은 벼락치기다(레딧 마이닝: 플래너류는 "만들어도 확인 안 함" — 행동 변화
  요구 제품의 실패 패턴). 현재 제품(D-day 인박스·⚡바로 초안·세션 완결 UX)이 이미
  이 모양이고 실사용 검증도 이 흐름에서 됐다.
- 그때그때 모델의 핵심 장치인 리마인드는 채널이 없다(웹뿐 — 푸시·이메일·카톡 부재).
  채널 확보는 9월 개강 전 구현 부담이 크고, 열어도 열람률 리스크가 있다.
- 재방문 KPI(30%)는 "다음 과제 때 다시 옴"으로 해석한다 — 과제는 학기 내내 계속
  나오므로, 원샷 경험이 좋으면 재방문은 따라온다.

## 하는 것 / 안 하는 것

- **하는 것:** 원샷 품질(유형 라우팅 정밀도·초안 품질·reask 안정성), 마감 임박 UX
  (인박스 임박 강조·⚡ 흐름), 한 세션 완결성(제안→finalize→내보내기 왕복 속도).
- **안 하는 것:** 체크포인트 3단계(상태 저장·리마인드)는 **중단**. 체크포인트
  플랜 1·2단계(볼륨 과제의 단계 표시·demo)는 표시 기능으로 유지 — 시간축 경계선
  안내는 남기되, 재방문을 제품이 강제로 만들지 않는다.

로드맵 Tier 4-14의 예시였던 "마감 리마인드"도 이 결정으로 현재 구현 대상에서
제외한다. 토큰 없이 여는 공개 데모와 인박스 D-day·임박 강조가 현재 온보딩·리텐션
범위다. 아래 재검토 조건이 충족되기 전에는 알림 권한이나 외부 발송 채널을 추가하지
않는다.

## 재검토 조건 (텔레메트리 — 2026-08-05 배포분으로 측정 가능)

9월 베타 4주 데이터에서 아래가 관찰되면 그때그때 방향을 재평가한다:

1. 초안 생성 시점의 `deadline_bucket` 분포에서 `D-7+`가 유의미한 비중(예: 30%+)
   — 미리 하는 사용자가 실재한다는 뜻.
2. 같은 과제(assignment_key)의 stage 방출이 여러 날짜에 걸침 — 이어서 하기가
   자연 발생한다는 뜻.
3. 체크포인트 패널 노출 과제의 재방문이 비노출 대비 뚜렷이 높음.

측정 필드는 이미 있다(`deadline_bucket`·`stage`·`date`·`user_seconds`·uid 퍼널).
추가 계측이 필요한 것은 체크포인트 패널 열람 이벤트뿐이며, 재검토 시점에 붙인다.
