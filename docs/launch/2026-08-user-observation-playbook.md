# 2026년 8월 실사용 관찰 플레이북

## 목적

이 관찰의 목표는 기능 칭찬을 모으는 것이 아니라 이탈 지점 두 종류를 찾는 것이다. 첫째는
결과물의 품질이 깨져 사용자가 “이건 못 쓰겠다”고 판단한 **신뢰를 잃은 순간**, 둘째는
조작이 번거롭거나 반복돼 사용을 멈춘 **짜증난 순간**이다. 관찰자는 만족도를 대신 해석하지
않고, 사용자가 실제 과제로 어디까지 혼자 진행하는지와 멈춘 바로 그 순간을 기록한다.

## 모집

- 3~5명을 모집한다.
- 각 참여자는 **본인의 진짜 과제 1개 이상**을 가져온다. Phase 5 게이트를 판정할 참여자는
  각자 실제 과제 2개 이상에서 사용해야 한다.
- 샘플·가짜 과제는 사용자가 품질과 제출 위험을 진지하게 판단하지 않으므로 관찰 자료로
  세지 않는다.
- 과제 원문, 제목, eTL 토큰, 결정 질문 답변은 관찰 보고서나 공유 문서에 옮기지 않는다.

## 세션 진행 대본 (15~25분)

**관찰자는 먼저 설명하지 않는다.** 사용자가 막혀도 바로 기능이나 정답을 알려주지 말고,
먼저 행동·화면·발화를 기록한다. 안전 문제, 자격증명 노출, 데이터 손실 위험이 있을 때만
즉시 개입한다. “지금 무슨 생각이 드세요?”는 평가나 해결책을 유도하지 않는 질문으로 쓴다.

| 구간 | 관찰자가 할 일 | 질문을 던질 타이밍 |
|---|---|---|
| 홈 | URL만 열어 주고 손을 뗀다. 서비스가 무엇을 해 준다고 이해하는지 본다. | 첫 클릭 전: “이게 무엇을 하는 서비스로 보여요?” 이어서 “지금 무슨 생각이 드세요?” |
| eTL 연결 (`/connect`) | 토큰 요구를 읽는 표정, 망설임, 이탈·대체 경로 선택을 본다. 토큰 위치를 먼저 알려주지 않는다. | 토큰 입력을 멈추거나 다른 탭을 찾을 때: “지금 무슨 생각이 드세요?” |
| 붙여넣기·과제 등록 (`/simple`, `/new`) | 본인의 실제 과제를 넣게 한다. 붙여넣기와 칸 입력 중 무엇을 고르고 어디서 막히는지 본다. | 입력 방식을 고른 직후와 제출 버튼 앞에서 각각 한 번 묻는다. |
| 초안 첫 대면 | 첫 10초의 시선, 스크롤, 원문 대조, 즉시 수정·닫기 행동을 기록한다. **신뢰 판정이 여기서 갈린다.** | 결과를 읽기 시작한 뒤 침묵이 생기거나 첫 반응이 나온 직후: “지금 무슨 생각이 드세요?” |
| 결정 질문 4개 (`SIMPLE_FIRST_N`) | 네 질문이 실제로 답할 만한지, 건너뛰는지, “나머지는 나에 맞춰 채워줘”를 누르는지 본다. | 각 질문에서 멈춘 순간과 자동 채우기 선택 직전: “이 질문에 답할 수 있을 것 같아요?” |
| 완성본·제출 파일 | 완성본을 그대로 쓸 수 있다고 보는지, 복사·다운로드·재수정 횟수를 센다. | 첫 수정 또는 다운로드 선택 직전: “지금 이 결과를 제출에 쓸 수 있겠어요? 왜 그렇게 느꼈어요?” |
| 제출 직전 (`/ready/<token>`) | 점검 항목을 읽는지, 제출 파일과 eTL 이동 경로를 찾는지, 되돌아가는지 본다. | 제출 행동을 멈추거나 같은 화면을 두 번 오갈 때: “지금 무슨 생각이 드세요?” |
| 완성 후 로그인 유도 | 이미 얻은 가치가 로그인 의향으로 이어지는지 본다. 가입을 설득하지 않는다. | 로그인 안내를 본 직후: “지금 로그인할 마음이 드세요? 그렇게 느낀 이유는 뭐예요?” |

## 기록 양식

**해석을 적지 말고 본 것만 적는다.** “신뢰가 낮음” 대신 “초안 첫 문단을 읽고 ‘근거가
없어서 못 쓰겠다’고 말한 뒤 탭을 닫음”처럼 행동과 발화를 기록한다. 발화는 가능한 한 그대로
쓰되 과제 원문·제목·이름·학번·토큰은 남기지 않는다.

| 시각 | 화면 | 관찰된 행동 | 발화 그대로 | 분류 (신뢰상실 · 짜증 · 혼란 · 긍정) | 심각도 (1~3) |
|---|---|---|---|---|---:|
| 00:00 |  |  |  |  |  |

심각도 1은 잠깐 멈췄지만 스스로 회복, 2는 우회·질문이 있어야 진행, 3은 제출을 포기하거나
관찰자 도움 없이는 진행 불가로 기록한다.

## Phase 5 지표와 연결

| 계획서의 측정 항목 | 이 세션에서 재는 방법 |
|---|---|
| 과제 열기 → 작업 시작까지 시간 | 실제 과제 화면을 연 시각부터 Until에서 첫 초안 생성 행동을 누른 시각까지 스톱워치로 잰다. |
| 제출 bundle까지 클릭·복사·업로드 수 | 홈부터 제출 파일 확보까지 클릭, 복사, 업로드를 각각 획 하나로 세고 합계를 기록한다. |
| Local Agent 실행 성공률 | 시도 수와 관찰자 개입 없이 수정 가능한 첫 결과까지 도달한 성공 수만 기록해 `성공/시도`로 계산한다. |
| validator 실패 후 자동 수정 성공률 | 실제 validator 실패가 난 시도 중 자동 수정 뒤 통과한 수를 `자동 통과/실패 발생`으로 기록한다. 실패가 없으면 추정하지 않는다. |
| 다음 과제 재사용 여부 | 같은 참여자가 두 번째 실제 과제를 새 세션에서 시작했는지 기록하고, 관리자 `draft`와 텔레메트리 `stage=draft` 집계로 보조 확인한다. |

준비시간 70% 감소는 같은 참여자가 해당 과제를 Claude/ChatGPT로 수동 준비할 때의 실제
기준시간과 Until 시간을 모두 남긴 경우에만 계산한다. 회상 추정이나 근거 없는 시간은 쓰지
않는다. 관리자 이벤트는 누적 횟수이고 텔레메트리 `user_seconds`는 초안 이후 체류시간이므로,
과제 열기부터 작업 시작까지의 시간과 클릭·복사·업로드 수는 현장 기록이 기준이다.

### 관찰 로그와 자동 집계

세션 뒤 다음 명령으로 관리자 이벤트와 비식별 텔레메트리를 함께 확인한다.

```bash
python tools/observation_report.py --users-root _until_work/users
python tools/observation_report.py --users-root _until_work/users --since 2026-08-20
```

현재 웹은 `visit`, `connect`, `login`, `assign_open`, `draft`, `final`, `export`,
`submitted` 등을 호출한다. 다만 관리자 허용 목록에 실제 저장되는 관찰 관련 이벤트는
`visit`, `token_try`, `inbox`, `assign_open`, `draft`, `decision_ans`, `decision_skip`,
`final`, `export`와 고정 실패 이벤트다. 따라서 보고서의 연결은 `token_try`/`inbox`,
제출표시는 `export`를 근접 신호로 쓰며, 이것을 실제 연결 완료나 eTL 제출 완료로 과장하지
않는다. 텔레메트리는 동의된 비식별 `draft`/`final`/`export` stage만 보강한다.

## 진행·중단 기준

Phase 5를 통과하려면 다음 기준을 **모두** 만족해야 한다.

- 3명 이상이 각 2개 이상의 실제 과제에 사용
- 60% 이상이 다음 과제에서 재사용
- 준비시간 중앙값 70% 이상 감소
- API 원가 0원 유지

기준에 미달하면 Code/HDL 확장을 중단한다. 먼저 설치 마찰을 제거하고, 다음으로 로그인·eTL
연결 이탈을 고치며, 마지막으로 초안부터 제출 bundle까지의 작업공간 UX를 고친다. 측정하지
못한 항목은 통과로 간주하지 않는다.

## 세션 후 30분 루틴

1. 0~10분: 관찰 표에서 개인정보를 제거하고, 행동·발화가 빠진 해석 문장을 지운다.
2. 10~20분: 심각도 3→2→1 순으로 정렬한다. 같은 이탈 원인의 반복은 한 항목으로 묶고
   발생한 참여자 수만 덧붙인다.
3. 20~30분: 상위 3건만 다음 스프린트 백로그에 넣고, 각 항목에 재현 화면과 확인할 지표를
   붙인다. 나머지는 버린다. 모두 고치려다 아무것도 못 고치는 것을 막기 위한 제한이다.
